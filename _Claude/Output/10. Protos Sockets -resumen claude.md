## 1. Aplicaciones de red

La comunicación entre procesos (IPC) depende de si están en el mismo host o en hosts distintos:
- **Mismo host**: definido por el S.O.
- **Diferentes hosts**: intercambio de mensajes sobre la red

El proceso que **inicia** la conexión es el **cliente**; el que **espera** conexiones es el **servidor**.

### Identificación de procesos

| Nivel | Identificador |
|---|---|
| Host | Dirección IP |
| Proceso dentro del host | Número de puerto |

Puertos conocidos: `80` (HTTP), `5432` (PostgreSQL).

### Responsabilidades del protocolo de aplicación

El protocolo de nivel de aplicación debe definir:
- **Tipos de mensaje** que se intercambian
- **Sintaxis** de los mensajes
- **Semántica** de los mensajes
- **Reacción frente a errores**

---

## 2. Interfaces de protocolos de transporte

El estándar TCP/IP sugiere que las API contemplen las siguientes operaciones básicas:

- Reservar recursos locales para la comunicación
- Especificar endpoints origen y destino
- Iniciar una conexión (cliente)
- Enviar un datagrama (cliente)
- Esperar una conexión (servidor)
- Enviar y recibir datos
- Determinar cuándo arriba información
- Generar y manejar datos urgentes

### APIs disponibles

| API | Origen |
|---|---|
| **Socket API** (Berkeley Sockets) | UNIX, años 80 |
| **Windows Socket** (WinSock) | Microsoft |
| **Transport Layer Interface (TLI)** | AT&T, System V UNIX |

## 3. Sockets: conceptos básicos

Berkeley Sockets fue diseñado para reutilizar system calls de UNIX (`open`, `close`, `read`, `write`) y extenderlos para comunicación en red. Soporta distintos protocolos (no solo TCP/IP).

Reglas fundamentales:

- El servidor debe estar en ejecución **ANTES** de que el cliente intente conectarse
- El servidor debe tener un **socket abierto** ("puerta") por el cual recibir y enviar mensajes
- Los clientes necesitan un socket propio
- Los clientes deben conocer la **IP y el número de puerto** del servidor

> [!note]
> Un servidor DNS, por ejemplo, escucha tanto TCP como UDP en el mismo puerto (53).

---

## 4. Socket API y file descriptors

Un proceso que necesita I/O usa el system call `open`, que crea un **file descriptor**. El S.O. implementa file descriptors como un vector de punteros a estructuras de datos (una tabla por proceso).

La API de sockets agrega una nueva abstracción: el **socket**. Al igual que con archivos, cada socket es identificado por un handle y almacenado en la tabla de file descriptors.

```
tabla de descriptores (por proceso)
fd 0 → struct para stdin
fd 1 → struct para stdout
fd 2 → struct para stderr
fd 3 → struct de socket { family: PF_INET, service: SOCK_STREAM, local IP, local port, remote IP, ... }
```

> [!note]
> Un socket es completamente general y puede usarse para que un server espere una conexión, o un cliente la inicie. No está limitado a TCP/IP.

## 5. Creación de un socket — `socket()`

```c
#include <sys/socket.h>
// Returns: file (socket) descriptor if OK, −1 on error
int socket(int domain, int type, int protocol);
```

### Parámetro `domain` — familia de protocolos

| Valor | Significado |
|---|---|
| `AF_INET` | IPv4 |
| `AF_INET6` | IPv6 |
| `AF_UNIX` | Comunicación local (mismo host) |
| `AF_UNSPEC` | Sin especificar |

### Parámetro `type` — tipo de comunicación

| Valor | Protocolo | Descripción |
|---|---|---|
| `SOCK_STREAM` | TCP, SCTP | Flujo de bytes secuencial, confiable, orientado a conexión |
| `SOCK_DGRAM` | UDP | Mensajes de longitud fija, sin conexión, no confiable |
| `SOCK_RAW` | IP | Interfaz directa a IP (opcional en POSIX.1) |
| `SOCK_SEQPACKET` | AF_UNIX, SCTP | Mensajes de longitud fija, secuenciados, confiables, orientados a conexión |

### Parámetro `protocol` — protocolo específico

Generalmente `0` para seleccionar el protocolo por defecto según `domain` y `type`. Valores posibles:

`IPPROTO_TCP`, `IPPROTO_UDP`, `IPPROTO_SCTP`, `IPPROTO_IP`, `IPPROTO_IPV6`, `IPPROTO_ICMP`, `IPPROTO_RAW`

> [!warning]
> Un error común es equivocarse entre el parámetro `type` y `protocol`. Son distintos niveles de especificación.

## 6. Flujo TCP cliente-servidor

```
Servidor                              Cliente
   |                                     |
socket()                              socket()
   |                                     |
bind()                                   |
   |                                     |
listen()                                 |
   |                                     |
accept() ←── bloquea ──────── connect() ─┘
   |         TCP 3-way handshake         |
   |                                     |
recv() ←──────────────────── send()      |
send() ──────────────────────→ recv()    |
   |                                     |
close()                              close()
```

### Analogía con telefonía celular

| Syscall | Analogía |
|---|---|
| `socket()` | Tener un teléfono para poder usarlo |
| `bind()` | Publicar el número de teléfono, pero en "modo avión" |
| `listen()` | Activar el teléfono (salir de modo avión) |
| `connect()` | Conocer el número del otro y marcarlo |
| `accept()` | Caller ID — se obtiene el ID una vez aceptada la conexión |
| `send()` / `recv()` | Hablar y escuchar |
| `close()` | Colgar |

## 7. Diseño de servidores

### 7.1 Servidor iterativo no orientado a conexión (UDP)

1. Crear un socket y ligarlo (`bind`) a un puerto
2. Leer un datagrama request de un cliente
3. Enviar datagrama/s como respuesta
4. Volver al paso 2

> [!note]
> Un datagrama es un mensaje auto-suficiente; no hay conexión que mantener.

### 7.2 Servidor iterativo orientado a conexión (TCP)

1. Crear un socket y ligarlo (`bind`) a un puerto
2. Aceptar un pedido de conexión a través del socket
3. Obtener un nuevo socket para la conexión (`accept`)
4. Leer un request del cliente
5. Enviar una respuesta
6. Si el cliente no finalizó, volver al paso 4
7. Cerrar el socket creado en paso 3
8. Volver al paso 2

### 7.3 Servidor concurrente orientado a conexión (fork)

**Problema con el servidor iterativo:** si un cliente pide un archivo de 200 MB y luego llega uno que pide 50 bytes, el segundo espera hasta que el primero termine.

**Solución:** fork por cada conexión.

```
Master (Proceso Padre)               Slave (Proceso Hijo)
1. Crear socket y bind a un puerto
2. Aceptar pedido de conexión
3. Crear proceso hijo (fork)  ──→   Atender la conexión
4. Volver al paso 2                 Interactuar con el cliente
                                    Cerrar conexión y terminar
```

> [!important]
> Al hacer fork, tanto padre como hijo tienen el socket de la conexión abierta. El padre debe cerrar el socket del hijo y el hijo debe cerrar el socket pasivo del padre para evitar leaks de descriptores.

## 8. Socket I/O — `shutdown()`

La comunicación en un socket es bidireccional. Se puede deshabilitar I/O en una dirección sin cerrar el socket:

```c
#include <sys/socket.h>
int shutdown(int sockfd, int how);
// Retorna: 0 (éxito) o -1 (error)
```

| Valor de `how` | Efecto |
|---|---|
| `SHUT_RD` | Deshabilita recepciones (reads) |
| `SHUT_WR` | Deshabilita transmisiones (writes) — **envía FIN** |
| `SHUT_RDWR` | Deshabilita ambas direcciones |

## 9. Formato de direcciones

### `struct sockaddr` — genérico

Una dirección identifica un socket endpoint. El formato es específico para cada familia y se castea a un formato genérico:

```c
struct sockaddr {
    sa_family_t sa_family;   // address family
    char        sa_data[...]; // variable-length address
};
```

### `struct sockaddr_in` — IPv4

```c
struct in_addr {
    in_addr_t s_addr;  // IPv4 address (uint32_t)
};

struct sockaddr_in {
    sa_family_t    sin_family;  // address family (unsigned short)
    in_port_t      sin_port;    // port number (uint16_t)
    struct in_addr sin_addr;    // IPv4 address (uint32_t)
    unsigned char  sin_zero[8]; // relleno (Linux)
};
```

Uso con `bind`:
```c
struct sockaddr_in myAddress;
// ...
bind(socket, (struct sockaddr *) &myAddress, sizeof(myAddress));
```

> [!note]
> El campo `s_addr` de `struct in_addr` puede tener el valor especial `INADDR_ANY` en un socket pasivo. Indica que se aceptan conexiones en **cualquiera de las interfaces** del host.

### `struct sockaddr_in6` — IPv6

```c
struct in6_addr {
    uint8_t s6_addr[16];  // IPv6 address (128 bits)
};

struct sockaddr_in6 {
    sa_family_t    sin6_family;   // address family (unsigned short)
    in_port_t      sin6_port;     // port number (uint16_t)
    uint32_t       sin6_flowinfo; // traffic class and flow info
    struct in6_addr sin6_addr;   // IPv6 address
    uint32_t       sin6_scope_id;
};
```

## 10. Resolución de nombres

Un cliente que solo conoce el FQDN del servidor necesita resolverlo a una dirección IP antes de conectarse.

| Función | Descripción |
|---|---|
| `inet_addr` | Convierte de notación con puntos ("200.132.2.15") a decimal |
| `gethostbyname` | Dado un FQDN, retorna estructura con IP decimal (deprecated) |
| `getaddrinfo` | Más completa y moderna, recomendada |

### `getaddrinfo()`

```c
#include <sys/socket.h>
#include <netdb.h>
int getaddrinfo(const char *restrict host,
                const char *restrict service,
                const struct addrinfo *restrict hint,
                struct addrinfo **restrict res);
void freeaddrinfo(struct addrinfo *ai);
```

> [!note]
> `getaddrinfo` es **sincrónica**. Existe una versión asincrónica: `getaddrinfo_a`.

### `struct addrinfo`

| Campo | Tipo | Descripción |
|---|---|---|
| `ai_flags` | `int` | Personaliza el comportamiento (ej: `AI_PASSIVE` para socket pasivo, `AI_CANONNAME` para nombre canónico) |
| `ai_family` | `int` | Familia: `AF_INET`, `AF_INET6`, `AF_UNSPEC` |
| `ai_socktype` | `int` | Tipo: `SOCK_STREAM` (TCP), `SOCK_DGRAM` (UDP) |
| `ai_protocol` | `int` | Protocolo: `IPPROTO_TCP`, `IPPROTO_UDP`, o `0` para auto |
| `ai_addrlen` | `socklen_t` | Longitud en bytes de `ai_addr` |
| `ai_addr` | `struct sockaddr *` | Puntero a la dirección de red |
| `ai_canonname` | `char *` | Nombre canónico del host (puede ser NULL) |
| `ai_next` | `struct addrinfo *` | Siguiente elemento en la lista (un host puede tener múltiples IPs) |

## 13. Multiplexing de I/O

Cuando un server maneja varios canales (distintos puertos, TCP y UDP, múltiples clientes), el I/O multiplexing permite atenderlos con un solo proceso sin bloquearse en uno específico.

### 13.1 `select()`

```c
int select(int n,
           fd_set *readfds,
           fd_set *writefds,
           fd_set *exceptfds,
           struct timeval *timeout);
```

- `n`: cantidad máxima de file descriptors a monitorear
- `readfds`, `writefds`, `exceptfds`: conjuntos de fd para read, write y condiciones excepcionales
- `timeout`: tiempo máximo de bloqueo (`NULL` = bloquear indefinidamente)

Los conjuntos son arrays de bits. Se manipulan con macros:

| Macro | Descripción |
|---|---|
| `FD_ZERO(fd_set *set)` | Inicializa el conjunto vacío |
| `FD_SET(int fd, fd_set *set)` | Agrega un fd al conjunto |
| `FD_CLR(int fd, fd_set *set)` | Elimina un fd del conjunto |
| `FD_ISSET(int fd, fd_set *set)` | Consulta si un fd está listo |

> [!warning]
> `select` tiene una **race condition** con señales: si una señal llega entre `sigaction` y `select`, la señal se pierde y `select` no es interrumpido.

### 13.2 `pselect()`

Resuelve la race condition de `select` bloqueando atomicamente las señales durante la llamada:

```c
int pselect(int n,
            fd_set *readfds,
            fd_set *writefds,
            fd_set *exceptfds,
            const struct timespec *timeout,
            const sigset_t *sigmask);
```

`sigmask` especifica señales a bloquear **durante** `pselect`. El kernel aplica atomicamente: bloquea señales → espera → restaura máscara original.

### 13.3 `poll()`

A diferencia de `select`, recibe un **vector** con únicamente los fd a escuchar (no un array de bits de tamaño fijo):

```c
int poll(struct pollfd *fds, unsigned int nfds, int timeout);

struct pollfd {
    int   fd;      // file descriptor
    short events;  // eventos que quiero vigilar
    short revents; // eventos que realmente ocurrieron
};
```

| Evento | Descripción |
|---|---|
| `POLLIN` | Hay datos disponibles para leer |
| `POLLOUT` | Se puede escribir sin bloquear |
| `POLLERR` | Error en el descriptor |
| `POLLHUP` | El otro extremo cerró la conexión |
| `POLLNVAL` | Descriptor inválido o no abierto |

### 13.4 `epoll` — multiplexing eficiente

Más eficiente que `select`/`poll` para gran cantidad de conexiones (escala O(1) vs O(n)):

```c
int epoll_create1(int flags);
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);

struct epoll_event {
    uint32_t events;  // EPOLLIN, EPOLLOUT, etc.
    union {
        void    *ptr;
        int      fd;
        uint32_t u32;
        uint64_t u64;
    } data;
};
```

- `epoll_create1`: crea la instancia epoll
- `epoll_ctl`: agrega/modifica/elimina fd del set monitoreado
- `epoll_wait`: bloquea hasta que un fd esté listo

> [!note]
> El campo `data` es una unión: epoll no interpreta su contenido. Se usa para asociar el fd o un puntero a estructura al evento.

## 14. Socket options

Permiten leer y modificar opciones de bajo nivel de un socket:

```c
#include <sys/socket.h>
int getsockopt(int socket, int level, int optionName,
               void *restrict optionValue, socklen_t *restrict optionLen);
int setsockopt(int socket, int level, int optionName,
               const void *optionValue, socklen_t optionLen);
// Retorna: 0 (éxito), -1 (error)
```

### Niveles disponibles

| Level | Aplica a |
|---|---|
| `SOL_SOCKET` | Opciones independientes del protocolo |
| `IPPROTO_TCP` | Específico de TCP |
| `IPPROTO_IP` | Protocolo de red IPv4 |
| `IPPROTO_IPV6` | IPv6 |

### Opciones `SOL_SOCKET`

| Opción | Descripción |
|---|---|
| `SO_BROADCAST` | Permite envío de broadcast (0/1) |
| `SO_KEEPALIVE` | Habilita keepalives en TCP |
| `SO_RCVBUF` | Tamaño en bytes del buffer de entrada |
| `SO_SNDBUF` | Tamaño del buffer de salida |
| `SO_RCVLOWAT` | Mínimo de bytes para procesar el input (default: 1) |
| `SO_SNDLOWAT` | Ídem para la salida |
| `SO_RCVTIMEO` | Timeout máximo para operaciones de lectura (default: 0 = sin timeout) |
| `SO_LINGER` | `0` envía RST al cerrar ("connection reset by peer"); si habilitado, `close` bloquea hasta que TCP envía toda la data pendiente |
| `SO_REUSEADDR` | Reusar dirección y puerto si el programa abortó |
| `SO_REUSEPORT` | Permite múltiples sockets en el mismo puerto |

### Opciones `IPPROTO_TCP`

| Opción | Descripción |
|---|---|
| `TCP_KEEPIDLE` | Segundos de inactividad antes del primer keepalive probe |
| `TCP_KEEPINTVL` | Intervalo en segundos entre probes sin respuesta |
| `TCP_KEEPCNT` | Máximo de probes sin respuesta antes de cerrar |
| `TCP_NODELAY` | Desactiva el **Algoritmo de Nagle** (que evita pequegramas reteniendo datos TCP brevemente para mejorar eficiencia) |

### Opciones `IPPROTO_IP` e `IPPROTO_IPV6`

| Opción | Descripción |
|---|---|
| `IP_TTL` | Time-to-Live del paquete (0-255) |
| `IP_MULTICAST_LOOP` | Permite al socket multicast recibir sus propios paquetes |
| `IP_ADD_MEMBERSHIP` | Unirse a un grupo multicast |
| `IP_DROP_MEMBERSHIP` | Abandonar un grupo multicast |
| `IPV6_V6ONLY` | Restringe el socket a solo IPv6 |

### Ejemplo: SO_LINGER

```c
int option_len = sizeof(struct linger);
struct linger ling;
int rc = getsockopt(s, SOL_SOCKET, SO_LINGER, (void *) &ling, &option_len);
if (rc == 0) {
    if (option_len == sizeof(ling)) {
        if (ling.l_onoff)
            /* yes, I linger */
        else
            /* no, I do not */
    }
}
```

## 15. Signals

### 15.1 Concepto

Un **signal** es un mecanismo para notificar a un proceso que ocurrió un evento (timeout, Ctrl-C, etc.).

El proceso puede:
- **Ignorar** la señal
- **Terminar** abruptamente
- **Interrumpir** su ejecución y ejecutar una rutina de manejo de señal (handler)
- **Bloquear** la señal temporalmente

### 15.2 Señales principales

| Señal | Evento | Acción por defecto |
|---|---|---|
| `SIGALRM` | Expiró un timer | Termina ejecución |
| `SIGCHLD` | `exit` de proceso hijo | Ignorar |
| `SIGINT` | Carácter interrupción (Ctrl-C) | Terminar |
| `SIGIO` | Socket listo para I/O | Ignorar |
| `SIGPIPE` | Intento de escribir en socket cerrado | Terminar |
| `SIGSEGV` | Segmentation fault | Terminar |
| `SIGTERM` | Terminación "amable" (`kill`) | Terminar |
| `SIGKILL` | Terminación forzosa | Terminar (no interceptable) |

### 15.3 `sigaction()` — cambiar comportamiento

```c
int sigaction(int signum, const struct sigaction *act,
              struct sigaction *oldact);

struct sigaction {
    void      (*sa_handler)(int); // SIG_IGN, SIG_DFL, o función
    sigset_t  sa_mask;            // señales a bloquear mientras ejecuta sa_handler
    int       sa_flags;           // modificadores de comportamiento
};
```

- `sa_handler`: si es `SIG_IGN` se ignora, `SIG_DFL` toma comportamiento por defecto, o una función que recibe el número de señal
- `sa_mask`: señales bloqueadas durante la ejecución del handler (para que no sea interrumpido)
- `oldact`: si no es NULL, guarda la acción previa (útil para restaurar después)

### 15.4 Manipulación de signal sets

```c
int sigemptyset(sigset_t *set);          // vacía el conjunto
int sigfillset(sigset_t *set);           // marca todas las señales
int sigaddset(sigset_t *set, int signal); // agrega una señal
int sigdelset(sigset_t *set, int signal); // elimina una señal
```

Ejemplo — ignorar SIGINT bloqueando también SIGTERM durante el handler:
```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGTERM);
sigaddset(&mask, SIGINT);
struct sigaction handler = {SIG_IGN, &mask, 0};
if (sigaction(SIGINT, &handler, NULL) < 0) {
    perror("failed trying to ignore SIGINT");
    return 1;
}
```

### 15.5 Ejemplo con handler personalizado

```c
void InterruptSignalHandler(int signalType) {
    puts("Interrupt Received. Exiting program.");
    exit(1);
}

int main(int argc, char *argv[]) {
    struct sigaction handler;
    handler.sa_handler = InterruptSignalHandler;
    if (sigfillset(&handler.sa_mask) < 0)
        ERROR("sigfillset() failed");
    handler.sa_flags = 0;
    if (sigaction(SIGINT, &handler, 0) < 0)
        ERROR("sigaction() failed for SIGINT");

    for (;;)
        pause(); // suspende hasta recibir señal
    exit(0);
}
```

### 15.6 Anidamiento de señales

> [!important]
> Las señales **NO se encolan**. Si se produce una señal mientras se está atendiendo otra, el manejo es **pospuesto** hasta que termina el handler actual. Si llegan múltiples señales del mismo tipo, solo se procesa una.

### 15.7 Signals y sockets

Si una señal llega mientras el proceso está **bloqueado** en una llamada de socket (`recv`, `connect`, `select`, etc.) y existe un handler para esa señal:

- El socket call retorna `-1`
- `errno = EINTR`

Patrón correcto para manejar esto:

```c
while (1) {
    errno = 0;
    int rc = recv(sock, buf, 1, 0);
    if (rc == -1 && errno == EINTR)
        continue; // fue interrumpido por señal, reintentar
    // manejar resultado real...
}
```

> [!note]
> El proceso también puede recibir `SIGPIPE` si intenta escribir en un socket cerrado por el otro extremo.

## 16. Blocking y timeouts

Las llamadas de I/O pueden bloquearse por diversas razones:

| Función | Razón del bloqueo |
|---|---|
| `recv()`, `recvfrom()` | No hay datos en el buffer de entrada |
| `send()` | No hay suficiente espacio en el buffer de salida |
| `sendto()` | Poco probable, pero puede bloquearse |
| `connect()`, `accept()` | Hasta que se completa la conexión |

**Problemas prácticos:**
- Un servidor puede querer hacer otras tareas mientras espera una conexión
- Los datagramas UDP pueden perderse y `recvfrom` bloquearse indefinidamente

## 17. Nonblocking I/O

Para "romper" el bloqueo existen tres estrategias:

| Estrategia | Descripción |
|---|---|
| Sockets no bloqueantes | `fcntl` con `O_NONBLOCK` |
| I/O asincrónico | El S.O. avisa con `SIGIO` cuando hay datos |
| Timeouts | Usar `SO_RCVTIMEO` u otras técnicas |

### 17.1 Sockets no bloqueantes con `fcntl()`

```c
#include <fcntl.h>
int s = socket(PF_INET, SOCK_STREAM, 0);
int flags = fcntl(s, F_GETFL, 0);
fcntl(s, F_SETFL, flags | O_NONBLOCK);
```

Con `O_NONBLOCK`, si la operación no puede completarse de inmediato, la función retorna error en lugar de bloquearse.

### 17.2 Comportamiento no bloqueante

| Situación | Comportamiento |
|---|---|
| Función necesitaba bloquear | Retorna -1 con `errno = EWOULDBLOCK` |
| UDP `send()` / `sendto()` | No bloquea (no hay buffer de salida) |
| TCP `connect()` | Retorna -1 con `errno = EINPROGRESS` |
| `getaddrinfo()` | **SÍ bloquea** siempre (sincrónica por diseño) |

### 17.3 Ejemplo de uso

```c
// recvfrom no bloqueante
numBytesRcvd = recvfrom(servSock, buffer, MAXSTRINGLENGTH, 0,
                        (struct sockaddr *) &clntAddr, &clntLen);
if (numBytesRcvd < 0) {
    if (errno != EWOULDBLOCK)
        ERROR("recvfrom() failed");
    // si es EWOULDBLOCK: no había datos, continuar con otras tareas
}

// connect no bloqueante
do {
    res = connect(soc, (struct sockaddr *) &addr, sizeof(addr));
    if (res < 0) {
        if (errno == EINPROGRESS) { putchar('.'); continue; }
        ERROR;
    }
} while (res != 0);
```

> [!warning]
> **Nunca hacer "polling" activo** (loop sin pausa esperando `EWOULDBLOCK`). Consume CPU innecesariamente. Usar `select`/`poll`/`epoll` para saber cuándo el fd está listo.

### 17.4 I/O asincrónico con SIGIO

En vez de hacer polling, el S.O. avisa cuando un socket call está listo. El programa realiza otras tareas y solo interrumpe su flujo al recibir `SIGIO`.

Pasos:
1. Usar `sigaction()` para registrar un handler para `SIGIO`
2. Usar `fcntl()` para hacerse owner del socket (`F_SETOWN`)
3. Usar `fcntl()` para habilitar `O_NONBLOCK` en el socket

Ver ejemplo: `UDPEchoServer-SIGIO.c`

## 18. Resumen de estrategias de I/O

| Técnica | Mecanismo | Cuándo usar |
|---|---|---|
| **Bloqueante** | Llamada queda suspendida | Un solo canal, flujo simple |
| **Multiplexing select** | Array de bits, O(n), con `timeout` | Múltiples fd, compatible amplio |
| **Multiplexing poll** | Vector de pollfd, O(n) | Más de 1024 fd, sintaxis más clara |
| **Multiplexing epoll** | Event-driven, O(1) | Gran cantidad de conexiones (servers de alta carga) |
| **No bloqueante + polling** | `O_NONBLOCK` + loop | Evitar, consume CPU |
| **I/O asincrónico (SIGIO)** | S.O. notifica con señal | Arquitecturas event-driven simples |
