# Frontend Architecture

This document explains how the TEL frontend works in this repository. It is written from the point of view of the current implementation, not from the original Flex/Bison template. The frontend is the part of the compiler that reads TEL source code, turns it into tokens, parses those tokens according to the TEL grammar, builds an abstract syntax tree, and reports whether the input program is accepted or rejected.

At the moment, the project stops after syntactic analysis. There is no active semantic-analysis phase, type checker, symbol table, or C code generator wired into the executable.

## High-Level Pipeline

The active pipeline is:

```text
stdin
  -> Flex scanner
  -> lexer actions
  -> Bison push parser
  -> parser semantic actions
  -> AST stored in CompilerState
  -> recursive AST cleanup
```

The executable accepts TEL source through standard input. The normal way to run a file is:

```bash
src/main/bash/run.sh program.tel
```

The script pipes the file into `.build/Flex-Bison-Compiler`. The compiler then either exits with `0` when the frontend accepts the program or with a non-zero value when the frontend rejects it.

## Main Files

The frontend is split across these source files:

| File | Responsibility |
| --- | --- |
| `src/main/c/EntryPoint.c` | Creates shared compiler objects, initializes modules, starts parsing, destroys the AST, and shuts everything down. |
| `src/main/c/frontend/Frontend.c` | Owns the scanner/parser bridge. It creates the `LexicalAnalyzer`, runs `yylex`, and pushes tokens into Bison. |
| `src/main/c/frontend/lexical-analysis/FlexPatterns.l` | Defines lexical patterns: keywords, literals, operators, comments, indentation handling entry points, inline C blocks, and punctuation. |
| `src/main/c/frontend/lexical-analysis/FlexActions.c` | Implements what happens when Flex matches a lexeme: token creation, token semantic values, indentation stack updates, typedef relabeling, EOF handling, and inline C buffering. |
| `src/main/c/frontend/lexical-analysis/StackADT.c` | Small integer stack used by the lexer to track indentation levels. |
| `src/main/c/frontend/syntactic-analysis/BisonGrammar.y` | Defines the grammar and operator precedence. Bison generates `BisonParser.c` and `BisonParser.h` from this file. |
| `src/main/c/frontend/syntactic-analysis/BisonActions.c` | Allocates AST nodes for grammar reductions, tracks typedef names, stores the root AST in `CompilerState`, and performs implicit return conversion. |
| `src/main/c/frontend/syntactic-analysis/AbstractSyntaxTree.h` | Defines all AST node structs and enums. |
| `src/main/c/frontend/syntactic-analysis/AbstractSyntaxTree.c` | Recursively destroys AST nodes and the strings/subtrees they own. |
| `src/main/c/support/type/CompilerState.h` | Defines the shared compiler state. Currently it mainly stores the AST root. |
| `src/main/c/support/type/LexicalAnalyzer.h` | Defines the object that groups the Flex scanner, Bison parser state, logger, and source location pointer. |

Generated files also exist under the frontend directories:

```text
src/main/c/frontend/lexical-analysis/FlexScanner.c
src/main/c/frontend/lexical-analysis/FlexScanner.h
src/main/c/frontend/syntactic-analysis/BisonParser.c
src/main/c/frontend/syntactic-analysis/BisonParser.h
```

Those files are generated by Flex and Bison. They should not be edited manually.

## Program Startup

The compiler starts in `EntryPoint.c`.

The important startup steps are:

1. `createLexicalAnalyzer()` allocates a `LexicalAnalyzer`.
2. A logger named `EntryPoint` is created.
3. `CompilerState compilerState = {.abstractSyntaxtTree = NULL, .value = 0};` creates the shared state object.
4. Module initialization functions are called and their destructors are stored.
5. `executeSyntacticAnalysis()` runs the frontend.
6. If parsing succeeds, the backend section is skipped because it is commented out.
7. `destroyProgram(program)` frees the AST.
8. Module destructors run in reverse initialization order.
9. The logger and lexical analyzer are destroyed.

The module initialization order is:

```c
initializeAbstractSyntaxTreeModule()
initializeFlexActionsModule(lexicalAnalyzer)
initializeBisonActionsModule(&compilerState)
initializeFrontendModule(lexicalAnalyzer)
```

The reverse shutdown order matters because later modules may depend on earlier modules while they are active.

## The LexicalAnalyzer Object

`LexicalAnalyzer` is a small struct that groups the state needed by Flex and Bison:

```c
typedef struct {
    Logger * logger;
    void * location;
    void * parser;
    void * scanner;
} LexicalAnalyzer;
```

The fields are intentionally stored as `void *` because the concrete scanner and parser types are generated by Flex and Bison.

`createLexicalAnalyzer()` does the following:

1. Allocates the `LexicalAnalyzer`.
2. Allocates a `YYLTYPE` location object.
3. Creates a logger named `LexicalAnalyzer`.
4. Calls `yylex_init()` to initialize the Flex scanner.
5. Calls `yypstate_new()` to create Bison's push-parser state.
6. Enters Flex context `0`.

The parser is a push parser, not the more common pull parser. That means the project explicitly calls Bison with one token at a time through `yypush_parse()`.

## Frontend Control Loop

`executeSyntacticAnalysis()` in `Frontend.c` is the main frontend loop:

```c
CompilationStatus status = IN_PROGRESS;
while (status == IN_PROGRESS) {
    status = executeLexicalAnalysis(_lexicalAnalyzer);
}
```

`executeLexicalAnalysis()` calls `yylex(...)`. In this project, Flex actions do not simply return token labels to a caller that later invokes Bison. Instead, each lexer action usually creates a `Token`, pushes that token directly into the Bison parser, destroys the temporary token wrapper, and returns the parser status.

The loop continues while the parser returns `IN_PROGRESS`. It stops when parsing succeeds, parsing fails, or an out-of-memory status is returned.

The status values come from `CompilationStatus.h`:

```text
IN_PROGRESS
SUCCEEDED
FAILED
OUT_OF_MEMORY
```

## Token Creation

`createToken()` in `Frontend.c` builds a temporary `Token` object from the current Flex match:

1. `context` is copied from the current Flex context.
2. `label` is the Bison token label chosen by the lexer action.
3. `length` comes from `yyget_leng()`.
4. `lexeme` is copied from `yyget_text()`.
5. `line` comes from `yyget_lineno()`.
6. `semanticValue` is allocated as a `SemanticValue`.

The token wrapper is temporary. Once it is pushed into Bison with `pushToken()`, `destroyToken()` frees the wrapper, its copied lexeme, and the `SemanticValue` container.

This is why lexer actions must be careful with semantic values. When a token needs to give a string to Bison, the action stores a separate heap-allocated string in `token->semanticValue->string`. Bison then owns that string through the grammar value. The temporary token wrapper can be destroyed without losing the parser's semantic value.

## Flex Patterns

The scanner rules live in `FlexPatterns.l`.

The file defines reusable lexical patterns for:

| Pattern | Meaning |
| --- | --- |
| `integer` | Decimal integer literals. |
| `hexInteger` | Hexadecimal integer literals such as `0x2A`. |
| `octalInteger` | Octal integer literals such as `0o52`. |
| `float` | Floating-point literals with a decimal point or exponent. |
| `charLiteral` | Character literals with supported escapes. |
| `string` | Double-quoted string literals. |
| `whitespace` | Spaces, tabs, and carriage returns. |
| `terminator` | One or more semicolons. |
| `linebreak` | Newline. |
| `identifier` | C-like identifiers beginning with a letter or underscore. |
| `includeDirective` | `#include` followed by an identifier. |
| `defineDirective` | `#define` followed by a non-empty body ending before `;` or newline. |

Flex also defines exclusive scanner states:

| State | Purpose |
| --- | --- |
| `BOL` | Beginning-of-line state, used to measure indentation before reading the next real token. |
| `AFTER_POSTFIX` | State entered after identifiers, `)`, and `]` so the scanner can distinguish `->` pointer-member access from ordinary arrow syntax. |
| `INLINE_C` | State used while reading an inline C block delimited by backtick-only lines. |
| `BLOCK_COMMENT` | State used while skipping `/* ... */` comments. |

`YY_USER_INIT BEGIN(BOL)` starts scanning in beginning-of-line mode.

## Keywords and Reserved Words

`FlexPatterns.l` recognizes these keyword-like tokens before it recognizes ordinary identifiers:

```text
fn*
fn
ret
if
elif
else
ford
for
while
dw
switch
default
break
cnt
main
struct
enum
union
typedef
int
char
float
double
void
uint
uli
long
short
const
stc
null
```

Because these patterns appear before the identifier pattern, they cannot be used as normal identifiers. For example, `const` and `short` are reserved even when the parser would reject their use in some positions.

`stc` is the TEL spelling for the `STATIC` token. `cnt` is the TEL spelling for `CONTINUE`.

## Literals

The frontend currently tokenizes and parses these literal expressions:

| Literal | Token | AST expression kind |
| --- | --- | --- |
| Decimal integer | `INTEGER_LITERAL` | `EXPRESSION_INTEGER_LITERAL` |
| Hex integer | `INTEGER_LITERAL` | `EXPRESSION_INTEGER_LITERAL` |
| Octal integer | `INTEGER_LITERAL` | `EXPRESSION_INTEGER_LITERAL` |
| Float | `FLOAT_LITERAL` | `EXPRESSION_FLOAT_LITERAL` |
| Character | `CHAR_LITERAL` | `EXPRESSION_CHAR_LITERAL` |
| String | `STRING_LITERAL` | `EXPRESSION_STRING_LITERAL` |
| `null` | `NULL_LITERAL` | `EXPRESSION_NULL_LITERAL` |
| `{ ... }` | grammar-level array literal | `EXPRESSION_ARRAY_LITERAL` |

The frontend stores literal text as strings. It does not convert integer text to numeric values during parsing. For example, `0x2A`, `0o52`, and `42` all remain string payloads in the AST.

## Comments

The scanner ignores line comments and block comments:

```text
// line comment
/* block comment */
```

Line comments are ignored until newline. Block comments switch Flex into `BLOCK_COMMENT` mode until `*/` is found. Newlines inside block comments still trigger `LineBreakLexemeAction()`, so they are not completely invisible to the parser. An unclosed block comment reaches EOF in `BLOCK_COMMENT` mode and returns `FAILED` through `UnknownLexemeAction()`.

## Terminators

TEL treats newlines and semicolons as statement terminators.

The lexer maps:

```text
\n    -> LINEBREAK
;     -> SEMICOLON
;;;   -> one SEMICOLON token
```

The grammar then defines:

```bison
terminator:
    SEMICOLON
  | LINEBREAK
  ;
```

This means most grammar rules do not care whether a statement ended with a newline or a semicolon. Both satisfy `terminator`.

EOF handling also injects a final terminator before final dedents and the EOF token. This lets the last statement in a file parse cleanly even when the file does not end exactly the way an internal line would.

## Indentation

TEL uses indentation to delimit blocks, similar to Python. The scanner is responsible for turning indentation changes into `INDENT` and `DEDENT` tokens.

Indentation is handled by `FlexActions.c` with `_indentationStack`, a `StackADT` of unsigned integer indentation levels.

Initialization:

1. `initializeFlexActionsModule()` creates the indentation stack.
2. It pushes `0` as the base indentation level.

At the beginning of each non-blank line:

1. Flex is in `BOL` mode.
2. The rule `<BOL>[ \t]*[^ \t\n]` matches leading spaces/tabs plus the first non-whitespace character.
3. `IndentationLexemeAction()` counts spaces and tabs.
4. `yyless(0)` rewinds the match so the first real character is scanned again after indentation handling.
5. Flex enters `INITIAL` mode for normal token scanning.

Tabs count as 4 spaces. Any indentation level that is not a multiple of 4 is rejected.

If the new indentation is greater than the stack top:

1. The new level is pushed.
2. One `INDENT` token is emitted.

If the new indentation is equal to the stack top:

1. No indentation token is emitted.
2. Scanning continues.

If the new indentation is smaller than the stack top:

1. `_pushDedentsUntil(indentation)` pops indentation levels.
2. One `DEDENT` token is emitted for each popped level.
3. If the requested indentation does not match any existing stack level, parsing fails.

At EOF:

1. A final `SEMICOLON` token is emitted.
2. `_pushDedentsUntil(0)` emits all remaining dedents.
3. Token label `0` is pushed to Bison as EOF.

This design means the parser never counts spaces itself. The parser only sees explicit block delimiters: `INDENT` and `DEDENT`.

## Inline C Blocks

Inline C blocks are supported as frontend syntax nodes.

An inline C block begins with a backtick on a line by itself:

```text
`
int x = 1;
printf("%d", x);
`
```

The opening backtick rule enters the `INLINE_C` scanner state and resets the inline C buffer.

While inside `INLINE_C`:

1. Each content line is appended to `_inlineCBuffer`.
2. `IsInlineCClosingLine()` checks whether the current line is a closing backtick-only line.
3. When the closing line is found, `INLINE_C_BLOCK` is emitted.
4. The token semantic value is the accumulated C text.

The grammar accepts `INLINE_C_BLOCK` both as a top-level program item and as a statement inside function bodies. In the AST it becomes either:

```text
PROGRAM_ITEM_INLINE_C
STATEMENT_INLINE_C
```

The frontend only stores the text. It does not compile or validate the C code.

## Typedef Name Relabeling

Typedef handling is split between the parser and lexer.

When the parser reduces:

```bison
typedefDeclaration:
    TYPEDEF identifier COLON type terminator
```

`TypedefDeclarationSemanticAction()` allocates a typedef AST node and calls `_registerTypedefName(name)`.

The registered names are kept in a linked list in `BisonActions.c`.

Later, when Flex reads an identifier, `IdentifierLexemeAction()` asks:

```c
if (IsKnownTypedefName(token->lexeme)) {
    token->label = TYPEDEF_NAME;
}
```

So an identifier can become a `TYPEDEF_NAME` token if it was previously introduced by a typedef. This is order-dependent: a typedef name only works after its typedef declaration has already been parsed.

## Bison Parser Configuration

`BisonGrammar.y` configures Bison with:

```bison
%define api.pure full
%define api.push-pull push
%define api.value.union.name SemanticValue
%define parse.error detailed
%locations
```

The important parts are:

| Setting | Meaning |
| --- | --- |
| `api.pure full` | The parser avoids global parser variables where possible. |
| `api.push-pull push` | The parser consumes tokens through `yypush_parse()` one at a time. |
| `api.value.union.name SemanticValue` | The generated semantic-value union is named `SemanticValue`. |
| `parse.error detailed` | Bison can produce detailed errors, although `yyerror()` currently ignores them. |
| `%locations` | Location tracking is enabled, but detailed locations are not currently surfaced to users. |

`yyerror()` is currently empty:

```c
void yyerror(const YYLTYPE * location, const char * message) {}
```

That means frontend failures are primarily visible through the compiler exit status and optional logging, not through user-friendly parse error messages.

## Semantic Values

The grammar's `%union` defines the possible values attached to terminals and non-terminals.

Examples:

```bison
%union {
    char * string;
    TokenLabel token;
    Type * type;
    VariableDeclaration * declaration;
    FunctionDeclaration * functionDeclaration;
    Expression * expression;
    Statement * statement;
    Program * program;
}
```

Terminals such as identifiers and literals carry strings:

```bison
%token <string> IDENTIFIER
%token <string> INTEGER_LITERAL
%token <string> STRING_LITERAL
```

Punctuation and keyword tokens carry a token label:

```bison
%token <token> COLON
%token <token> RETURN
%token <token> FUNCTION
```

Non-terminals carry AST pointers:

```bison
%type <expression> expression
%type <statement> statement
%type <program> program
```

## Bison Destructors

The grammar declares destructors for semantic values:

```bison
%destructor { free($$); } <string>
%destructor { destroyExpression($$); } <expression>
%destructor { destroyStatement($$); } <statement>
```

These destructors are used by Bison to clean up values that are discarded during parse errors or parser shutdown.

The root `program` non-terminal intentionally does not have a `%destructor`. On success, the AST root must survive the parse and be stored in `CompilerState`. After parsing, `EntryPoint.c` explicitly calls `destroyProgram(program)`.

## Program Structure Grammar

The top-level grammar is:

```bison
program:
    optionalProgramItemList
  | optionalProgramItemList mainDeclaration optionalProgramItemList
  ;
```

This means a program can contain only ordinary top-level items, or it can contain a `main` declaration somewhere among ordinary top-level items.

Top-level items can be:

```text
variable declaration
function declaration
function pointer declaration
struct declaration
union declaration
enum declaration
typedef declaration
preprocessor directive
inline C block
empty item
```

Expression statements are not allowed at top level. A top-level function call or top-level assignment is rejected.

`main` is special. It is parsed by:

```bison
mainDeclaration:
    MAIN LINEBREAK functionBody
```

Because `main` is a keyword token, it is not parsed as an ordinary identifier and cannot be declared through `fn main`.

## Declarations

Variable declarations use name-first syntax:

```text
name: type
name: type = expression
stc name: type
stc name: type = expression
```

The grammar is:

```bison
declaration:
    identifier COLON type optionalInitializer terminator
  | STATIC identifier COLON type optionalInitializer terminator
  ;
```

The semantic action creates a `VariableDeclaration`:

```c
VariableDeclaration * declaration = calloc(1, sizeof(VariableDeclaration));
declaration->name = name;
declaration->type = type;
declaration->initializer = initializer;
declaration->isStatic = isStatic;
```

`stc` is only accepted where the grammar explicitly allows `STATIC`, such as top-level or statement variable declarations and static function declarations. It is not accepted for parameters or aggregate fields.

## Function Declarations

Function declarations use:

```text
fn name param1: type param2: type -> returnType
    statement
```

The grammar allows:

```text
fn name
fn name -> type
fn name params...
fn name params... -> type
stc fn name ...
```

The body is optional:

```bison
functionDeclaration:
    FUNCTION identifier optionalParameterList optionalReturnType terminator optionalFunctionBody
  | STATIC FUNCTION identifier optionalParameterList optionalReturnType terminator optionalFunctionBody
  ;
```

If no return type is specified, `optionalReturnType` creates a `void` type:

```bison
optionalReturnType:
    %empty
  | arrow type
  ;
```

Function parameters are whitespace-separated, not comma-separated:

```text
fn add a: int b: int -> int
```

Each parameter is:

```text
identifier: type
```

The AST stores a `FunctionDeclaration` with:

```text
name
parameters
returnType
body
isStatic
```

## Function Bodies and Statements

A function body is an indented statement list:

```bison
functionBody:
    INDENT statementList DEDENT
```

The parser never sees raw indentation spaces. It only sees the `INDENT` and `DEDENT` tokens emitted by the lexer.

Statements can be:

```text
variable declaration
function pointer declaration
return statement
expression statement
if statement
ford loop
for loop
while loop
do-while loop
switch statement
break statement
continue statement
inline C block
empty statement
```

Nested function declarations are not statements, so they are rejected inside function bodies.

## Return Statements

Return statements use `ret`:

```text
ret
ret expression
```

The grammar is:

```bison
returnStatement:
    RETURN optionalReturnExpression terminator
```

The AST stores return statements as `STATEMENT_RETURN`. The optional expression is stored in the statement's `expression` field. A bare `ret` has a `NULL` expression.

## Implicit Returns

After a function body is parsed, `FunctionBodyStatementListSemanticAction()` inspects the final non-empty statement in the body.

If that final statement is an expression statement and the expression has an approved shape, the statement kind is changed from:

```text
STATEMENT_EXPRESSION
```

to:

```text
STATEMENT_RETURN
```

Approved implicit-return expressions are:

```text
identifier
comparison: == != < > <= >=
logical binary: && ||
logical not: !expr
```

Other expression shapes stay as normal expression statements. For example, arithmetic expressions and function calls are not converted by this rule.

This is a parser-time AST rewrite. No extra node is allocated; the existing statement node is mutated.

## Conditionals

Conditionals use:

```text
if condition
    statements
elif condition
    statements
else
    statements
```

The grammar requires a terminator after each `if`, `elif`, and `else` header. In practice, that usually means a newline.

Internally:

1. Each `if` or `elif` branch becomes an `IfBranch`.
2. Branches are linked through `IfBranch->next`.
3. The optional `else` body is stored separately as a `StatementList *`.
4. The whole conditional is wrapped in a `STATEMENT_IF`.

An orphan `elif` is rejected because `ELIF` only appears in the grammar as part of an `ifStatement`.

## Loops

The frontend supports four loop forms.

### `ford`

`ford` is a range-style loop:

```text
ford i 0 10
    statements
```

The grammar is:

```bison
FORD identifier fordBound fordBound terminator INDENT statementList DEDENT
```

Each bound can be:

```text
identifier
integer literal
(expression)
```

The semantic action does not create a separate `ford` AST node. It lowers `ford i start end` into a regular `ForStatement` equivalent to:

```text
i = start
i < end
i++
```

The iterator name string is consumed and freed during that lowering.

### `for`

`for` is a C-style loop with comma-separated expressions:

```text
for init, condition, update
    statements
```

The three header parts are parsed as expressions and stored directly in the `ForStatement`:

```text
initializer
condition
update
body
```

### `while`

`while` is a pre-condition loop:

```text
while condition
    statements
```

It becomes `STATEMENT_WHILE`, which points to a `WhileStatement` containing the condition expression and body statement list.

### `dw`

`dw` is the frontend's do-while form:

```text
dw
    statements
condition
```

The grammar intentionally reads the condition expression after the body dedent:

```bison
DO_WHILE terminator INDENT statementList DEDENT expression terminator
```

It becomes `STATEMENT_DO_WHILE`.

## Switch Statements

Switch statements use:

```text
switch expression
    caseExpression:
        statements
    otherExpression -> statement
    default:
        statements
    default break
```

The grammar does not have a `case` keyword. A case is either an expression followed by `:` or an expression followed by `->`.

Block cases:

```text
value:
    statement
```

Inline cases:

```text
value -> statement
value -> statement; statement
```

Default cases:

```text
default:
    statement
default -> statement
default break
```

The AST represents all cases as `SwitchCase`. For `default`, `matchExpression` is `NULL`. For normal cases, `matchExpression` is the case expression.

Arrow cases implicitly append a `break` statement:

```c
AppendStatementListSemanticAction($3, BreakStatementSemanticAction())
```

So `x -> ret 1` behaves like an inline body ending with `break` at the AST level.

## Break and Continue

`break` is parsed as:

```text
break
```

and becomes `STATEMENT_BREAK`.

`cnt` is parsed as:

```text
cnt
```

and becomes `STATEMENT_CONTINUE`.

The frontend only checks that these tokens appear in statement positions allowed by the grammar. It does not currently verify whether they are inside a loop or switch. That would require semantic analysis.

## Aggregates

Structs and unions use indentation for their field lists:

```text
struct Point
    x: int
    y: int

union Value
    i: int
    f: float
```

The grammar is:

```bison
aggregateDeclaration:
    STRUCT identifier terminator INDENT aggregateFieldList DEDENT
  | UNION identifier terminator INDENT aggregateFieldList DEDENT
```

Fields are variable declarations without `stc`:

```text
fieldName: type
fieldName: type = expression
```

The AST stores aggregates as `AggregateDeclaration` with:

```text
kind: AGGREGATE_STRUCT_KIND or AGGREGATE_UNION_KIND
name
fields
```

Brace-style aggregate declarations are not part of the grammar.

## Enums

Enums use indentation:

```text
enum Color
    RED
    GREEN = 2
    BLUE
```

Each member has a name and an optional integer literal value:

```bison
enumMember:
    identifier optionalEnumMemberValue terminator
```

Comma-separated enum members are not supported. The enum member value is stored as a string if present.

## Typedefs

Typedef declarations use:

```text
typedef Name: type
```

A typedef does two things:

1. Creates a `TypedefDeclaration` AST node.
2. Registers the name so future lexer matches can emit `TYPEDEF_NAME`.

Because typedef tracking is parser-order dependent, this works:

```text
typedef Count: int
x: Count
```

but using `Count` before the typedef is parsed does not work as a typedef name.

## Preprocessor Directives

The frontend supports restricted preprocessor directives:

```text
#include name
#define body
```

The scanner captures the content after the directive keyword and stores it as the token's string semantic value.

For `#include`, the current pattern only accepts an identifier after `#include`. It does not accept C-style angle or string includes such as:

```text
#include <stdio.h>
#include "stdio.h"
```

For `#define`, the body must be non-empty and stops before a semicolon or newline.

The parser stores directives as `PreprocessorDirective` AST nodes with:

```text
kind
value
```

## Function Pointer Syntax

The frontend has two related function-pointer features.

First, a function pointer can be declared as a variable-like declaration:

```text
fn* callback int int -> int
fn* handler -> void
fn* tick
```

The grammar creates a `VariableDeclaration` whose type is `TYPE_FUNCTION_POINTER_KIND`.

Second, function-pointer types can appear inside ordinary type positions using parentheses:

```text
callback: (fn* int int -> int)
handler: (fn* -> void)
tick: (fn*)
```

Function-pointer parameter types are stored as a `ParameterList`, but bare type lists use `Parameter` nodes with `name = NULL`.

## Types

The grammar accepts primitive, named, pointer, array, function-pointer, and const-qualified types.

Primitive types:

```text
int
char
float
double
void
uint
uli
long
short
```

Named types:

```text
TypedefName
struct Name
enum Name
union Name
```

Pointer types:

```text
int*
struct Node*
```

Array types:

```text
int[10]
char[]
```

Const-qualified base types:

```text
const int
const struct Point
```

The `Type` AST node is a tagged struct:

```text
kind
name
pointee
arraySize
functionParams
returnType
isConst
```

For pointer types, `pointee` is the pointed-to type. For array types, `pointee` is the element type and `arraySize` is either an expression or `NULL`.

The grammar contains a comment warning that compound recursive forms such as `int*[3]`, `int[3][4]`, and `int[]*` parse, but their AST shape is not yet a stable contract.

## Expressions

Expressions are parsed into `Expression` AST nodes.

Primary expressions:

```text
identifier
integer literal
float literal
char literal
string literal
null
array literal
function call
(expression)
```

Function calls use comma-separated arguments:

```text
add(1, 2)
log("value", x)
```

Array literals use whitespace-separated expressions, not comma-separated expressions:

```text
{1 2 3}
```

Operators include:

```text
=
+ --
= -= *= /= %=
&= |= ^= <<= >>=
|| &&
| ^ &
== != < > <= >=
<< >>
+ - * / %
unary + unary - *addressTarget &value ! ~
array[index]
object.member
pointer->member
```

The grammar maps each operator to an `ExpressionOperator` enum value.

Binary operations store:

```text
kind = EXPRESSION_BINARY_OPERATION
operator
left
right
```

Unary operations store:

```text
kind = EXPRESSION_UNARY_OPERATION
operator
operand
```

Member access is represented as a binary operation. The left side is the object or pointer expression. The right side is an identifier expression for the member name.

## Operator Precedence

Operator precedence is declared in `BisonGrammar.y`, from lower to higher precedence:

```text
assignment and compound assignment
logical OR
logical AND
bitwise OR
bitwise XOR
bitwise AND
equality
comparison
shift
addition and subtraction
multiplication, division, modulo
unary operators
postfix increment/decrement, indexing, member access
```

Assignment operators are right-associative. Most binary operators are left-associative. Unary operators are right-associative.

This is broadly C-like, but the language grammar is still TEL-specific.

## AST Layout

The AST is defined in `AbstractSyntaxTree.h`.

The root node is:

```c
struct Program {
    ProgramItemList * items;
};
```

Most lists are singly linked lists:

```c
struct ProgramItemList {
    ProgramItem * item;
    ProgramItemList * next;
};
```

The same pattern is used for:

```text
VariableDeclarationList
ParameterList
EnumMemberList
ExpressionList
ProgramItemList
IfBranch
SwitchCase
StatementList
```

Variant nodes use a `kind` enum plus nullable fields. For example, `Statement` has:

```text
kind
variableDeclaration
expression
ifStatement
forStatement
whileStatement
doWhileStatement
switchStatement
inlineC
```

Only the field that matches `kind` should be considered meaningful.

## AST Allocation

All AST allocation is done with `calloc()` in `BisonActions.c`.

Each semantic action follows the same pattern:

1. Log the action name.
2. Allocate the AST node.
3. Fill the node fields from grammar values.
4. Return the node to Bison.

For example, variable declarations are created by:

```c
VariableDeclaration * declaration = calloc(1, sizeof(VariableDeclaration));
declaration->name = name;
declaration->type = type;
declaration->initializer = initializer;
declaration->isStatic = isStatic;
return declaration;
```

The semantic actions generally take ownership of the objects passed into them. If a grammar rule passes a string or subtree into an AST node, that AST node becomes responsible for freeing it later.

## AST Root Storage

When the whole program reduces, `ProgramSemanticAction()` creates the `Program` node and stores it in compiler state:

```c
Program * program = calloc(1, sizeof(Program));
program->items = items;
_compilerState->abstractSyntaxtTree = program;
return program;
```

`CompilerState` currently stores this pointer as `void * abstractSyntaxtTree`. The field name contains a typo, but that is the field used by the code.

After `executeSyntacticAnalysis()` returns, `EntryPoint.c` reads:

```c
Program * program = compilerState.abstractSyntaxtTree;
```

and later destroys it with:

```c
destroyProgram(program);
```

## AST Destruction and Ownership

`AbstractSyntaxTree.c` contains recursive destructors for every AST type.

The destructor style is:

1. Check for `NULL`.
2. Free owned strings.
3. Recursively destroy owned child nodes and lists.
4. Set pointers to `NULL`.
5. Free the node itself.

For example, `destroyExpression()` frees:

```text
value
functionCall
operand
left
right
elements
```

Then it frees the `Expression`.

This ownership model means an AST child should have exactly one owner. Sharing the same subtree pointer in two places would cause a double free. The current semantic actions avoid that by allocating separate identifier expressions when needed, such as in the `ford` lowering.

## Generated Build Flow

`CMakeLists.txt` wires generation and compilation together.

First, Bison generates:

```text
BisonParser.c
BisonParser.h
```

Then Flex generates:

```text
FlexScanner.c
FlexScanner.h
```

Flex depends on Bison because `FlexPatterns.l` includes `BisonParser.h` for token labels and semantic value definitions.

The executable explicitly lists all compiled source files:

```text
EntryPoint.c
Frontend.c
FlexActions.c
StackADT.c
FlexScanner.c
AbstractSyntaxTree.c
BisonActions.c
BisonParser.c
Environment.c
String.c
Logger.c
```

If a new `.c` file is added to the frontend, it must be added to `CMakeLists.txt` or it will not be compiled.

The normal build command inside the Docker container is:

```bash
src/main/bash/build.sh
```

That script removes `.build/`, deletes generated Flex/Bison outputs, regenerates everything through CMake, and runs `make`.

## Tests

Frontend tests live under:

```text
src/test/c/accept
src/test/c/reject
```

Accept tests must exit with status `0`. Reject tests must exit with a non-zero status.

The test runner is:

```bash
src/main/bash/test.sh
```

It runs every file in `accept` through the compiler and expects success, then every file in `reject` and expects failure.

The test suite covers declarations, terminators, functions, implicit returns, calls, operators, assignments, control flow, aggregates, typedefs, preprocessors, comments, inline C blocks, pointers, function pointers, member access, arrays, numeric and character literals, const, static storage, and integration examples.

## Current Frontend Boundaries

The frontend currently accepts or rejects syntax and builds an AST. It does not perform deeper semantic validation.

Not currently handled by the frontend pipeline:

```text
type checking
symbol table construction
scope checking
duplicate declaration checks
undefined identifier checks
checking break/cnt placement semantically
checking return type compatibility
C code generation
execution
constant folding
user-friendly parser error messages
```

Some syntax is intentionally rejected by the grammar:

```text
C-style declarations such as int x;
top-level function calls
top-level assignments
fn main as an ordinary function declaration
nested function definitions
C-style #include <stdio.h>
comma-separated enum members
comma-separated array literal elements
brace-style struct or union declarations
static parameters
static aggregate fields
stacked const qualifiers such as const const int
```

## How to Trace a TEL Program Through the Frontend

Consider:

```text
fn isPositive x: int -> int
    x > 0
```

The scanner emits roughly:

```text
FUNCTION
IDENTIFIER("isPositive")
IDENTIFIER("x")
COLON
TYPE_INT
ARROW
TYPE_INT
LINEBREAK
INDENT
IDENTIFIER("x")
GREATER_THAN
INTEGER_LITERAL("0")
LINEBREAK
DEDENT
EOF
```

The parser reduces:

1. `TYPE_INT` into a `Type` with `TYPE_INT_KIND`.
2. `x: int` into a `Parameter`.
3. `-> int` into the function return type.
4. `x > 0` into a binary `Expression`.
5. The expression plus terminator into an expression `Statement`.
6. The indented statement list into a function body.
7. The final expression statement into an implicit return because `>` is an approved implicit-return operator.
8. The function declaration into a `ProgramItem`.
9. The item list into a `Program`.

The final AST root is stored in `CompilerState.abstractSyntaxtTree`. After parsing, the current executable destroys that AST and exits.

## Practical Notes for Future Frontend Work

When changing the frontend, keep these constraints in mind:

1. Add new tokens in `BisonGrammar.y` and update `FlexPatterns.l` to emit them.
2. If a token carries data, set the correct `semanticValue` field in `FlexActions.c`.
3. If a grammar rule creates a new AST shape, add or update structs/enums in `AbstractSyntaxTree.h`.
4. Add allocation helpers in `BisonActions.c`.
5. Add recursive cleanup in `AbstractSyntaxTree.c`.
6. Add the source file to `CMakeLists.txt` if a new `.c` file is introduced.
7. Add accept and reject tests for the new syntax.
8. Rebuild through Docker so generated files match the Linux grading environment.

The most important ownership rule is simple: once a semantic action stores a string or child pointer inside an AST node, that AST node owns it and its destructor must free it exactly once.
